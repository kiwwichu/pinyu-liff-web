# Pinyu 整合平台需求草稿

狀態：持續收集需求
建立日期：2026-08-19

這份文件記錄新系統需要保留、改善與新增的功能。內容尚未代表最終資料庫或畫面設計；未確認的規則會明確標成「待確認」，避免把猜測寫進正式系統。

## 開發原則

- 舊的 Google Sheets、Apps Script、Vercel 與正式 LINE 功能在新系統測試完成前繼續運作。
- Supabase 將成為正式切換後的唯一資料來源，不另外建立新的試算表保存抽成或合約資料。
- 客戶端、保姆端與管理後台共用同一套訂單、計價、付款與權限規則。
- 先完成一條可測試的訂單完整流程，再逐步取代舊功能。
- 前端採響應式設計，同一套系統支援電腦、平板與手機，不為三種裝置維護三套不同程式。
- 可使用實際持有的裝置作為重點驗收機型，但版面仍須適應其他常見螢幕尺寸、方向與瀏覽器。
- Supabase 是資料儲存與後端基礎設施，不是經營者日常操作介面；正式切換前必須建立能完整取代 Google Sheets 日常工作的管理後台。
- 不以要求經營者直接進 Supabase Table Editor 修改資料作為正式操作流程；一般新增、修改、查詢與狀態處理都應由 Pinyu 後台完成。
- 新後台的功能完整度至少不得低於目前 Google Sheets，並改善畫面、操作流程、資料驗證、自動計算與權限安全。

## 0. 整合介面與跨裝置使用

### 目標

- 建立一個整合客戶端、保姆端與管理後台的網站系統；登入後依角色顯示有權使用的功能。
- 電腦版適合大量資料、報表與訂單管理，平板與手機版適合外出查看、現場操作、簽名與快速更新狀態。

### 必要功能

- 採響應式版面，依可用寬度調整導覽列、欄位排列、訂單卡片、表格與操作按鈕。
- 手機不得只是把電腦表格縮小；重要資料需改成易讀卡片或可展開明細，常用按鈕需方便觸控。
- 平板同時支援直向與橫向；電腦版有效利用較寬畫面，但不影響較小筆電。
- 所有重要流程都需實機測試：登入、新增／修改訂單、查看未付尾款、保姆指派、行事曆同步、合約查看與簽名。
- 建立共用的文字大小、色彩、間距、按鈕、表單、卡片與錯誤提示規則，避免各頁面看起來像不同系統。
- 第一階段以網站／LIFF 響應式介面為主，不另外製作需要上架商店的原生手機 App。

### 待取得資訊

- 使用者手上要列為重點驗收的手機、平板與電腦型號、作業系統及常用瀏覽器。
- 各角色在手機與電腦上最常使用的前三個操作，作為導覽與首頁排序依據。

### 經營者管理後台（第一優先）

- 經營者帳號具有完整管理視野，可集中查看客戶、毛孩、訂單、服務時段、付款與尾款、保姆指派、抽成與結算、評價、合約、行事曆同步及系統處理狀態。
- 管理後台必須能新增訂單，並支援修改、確認、取消、付款登記、保姆指派與逐項金額對帳。
- 「由經營者在後台新增訂單」優先於「客戶自行送出新預約」，因為目前主要客群仍為舊客戶，實際訂單多由經營者處理。
- 後台需有評價列表與評價詳情，可依客戶、保姆、服務日期、分數及處理狀態查找。
- 所謂完整管理視野仍需保留敏感資料的明確操作與稽核紀錄，避免身分證等資料在一般列表無意間完整顯示。
- 每一類日常資料需提供適合業務使用的列表、搜尋、篩選、排序、詳情、新增、修改與停用／封存功能；系統識別碼與技術欄位不必暴露給經營者手動處理。
- 常用欄位需有清楚名稱、格式提示與輸入驗證；訂單金額、未付尾款、抽成及結算由系統自動計算，避免依賴試算表公式或人工心算。
- 重要修改需保留修改時間、修改者與前後內容；一般操作優先採停用、取消或封存，避免誤刪後無法復原。
- 保留必要的匯出能力，方便對帳、備份或另行分析；大量資料操作是否需要批次修改，依現行試算表工作流程盤點後決定。
- 新增訂單同時支援「建立空白訂單」與「複製既有訂單再修改」，不強迫所有案件只能使用同一個建立方式。
- 複製舊訂單時需明確顯示目前會員資料與舊訂單快照的差異，例如客戶已搬家；由經營者確認本次要採用的地址與費用，不能靜默覆蓋。
- 會員主檔、毛孩資料、價目表與車馬費規則只提供新訂單預設值；正式訂單確認後，實際地址、價格、費用與計算規則保存為該單快照。
- 客戶搬家、預設車馬費調整、服務單價變更或保姆抽成比例改變，只影響後續新訂單；歷史訂單保留成立當下的資料與金額。
- 歷史訂單若確需補正，必須透過有修改紀錄的更正流程，不使用會讓所有舊資料跟著重新計算的共用公式。

### 服務分類與客製價格

- 服務項目以少量、穩定的大分類管理，例如到府照顧、散步、長時間陪伴；不再為每一種客製價格建立一個永久下拉選項。
- 每個大分類可有一般參考價格，但不是強制所有客戶使用同一價格。
- 可為個別客戶保存各服務分類的約定單價與生效時間；建立新訂單時優先帶入該客戶目前有效的約定價格。
- 訂單內仍可修改本次單價、名稱、次數與說明，也可新增只使用一次的自訂服務項目。
- 訂單確認後保存本次實際服務名稱、單價、數量與小計快照；日後修改一般價格或客戶約定價格，不得重算歷史訂單。
- 後台需清楚標示價格來源，例如「一般參考價」、「客戶約定價」、「複製舊單」或「本單人工調整」，方便日後理解金額由來。
- 客戶約定價格變更需保留歷史與生效日期，不能覆蓋掉舊價格後失去過往依據。

### 後台通知中心

- 通知中心取代大量即時彈窗，避免訂單與會員數增加後造成通知疲勞。
- 通知至少依下列類型分類：客戶資料異動、訂單、付款／尾款、保姆與指派、合約、評價、Google 行事曆、LINE 通知及系統錯誤。
- 每筆通知保存重要程度、未讀／已讀、待處理／已完成、發生時間、相關客戶／訂單及可直接前往處理的連結。
- 後台可依類型、重要程度、處理狀態、日期與關聯人員篩選；首頁只突出真正需要處理的數量與高優先通知。
- 同一事件重複發生時需防止洗版，可更新既有通知、合併同類事件或保留次數，而不是無限制新增相同訊息。
- 客戶地址變更後自動建立「客戶資料異動」通知，顯示變更時間與前後差異；若有未來已成立訂單，通知需標記為待處理並列出受影響訂單。
- 低風險通知可標記已讀或封存；需要人工決定的通知必須有完成／略過原因，保留處理者與時間。
- 已處理或已過一段時間的一般異動通知可從主要待辦移入「其他異動紀錄／歷史紀錄」，仍可依客戶、訂單、類型與日期查找。
- 保姆第一次打開包含重要異動的已指派訂單時，相關欄位需醒目標示，例如「地址已更新」；標示持續到保姆查看或按下確認已知悉，並保存查看／確認時間。
- 只有已指派訂單實際服務地址被更新時才通知保姆；客戶會員主檔改地址但尚未套用到該訂單時，不提前把新地址透露給保姆。
- 背景推播內容不得在手機鎖定畫面直接顯示完整地址或其他敏感資料，只顯示「某訂單的重要資料已更新」，點擊並通過登入後才查看詳情。

### 保姆通知通道

- 系統內通知與重要異動標示是基本功能，不依賴保姆是否開啟背景推播。
- 保姆可自行選擇背景通知通道與開關，例如 LINE 通知及安裝式網站的 Web Push；後台保存每個裝置的訂閱與最後有效狀態。
- 關鍵安全異動採「系統內醒目提示＋LINE 通知」為主要方案；Web Push 作為保姆安裝 PWA 後可選擇開啟的額外通道。
- 網站以 PWA 形式安裝到手機主畫面後，可在網頁關閉時透過 Service Worker 接收 Web Push；需使用 HTTPS、由使用者主動允許通知並建立推播訂閱。
- iPhone／iPad 的 Web Push 需使用支援版本並將網站加入主畫面；LINE LIFF 瀏覽器不支援 Service Worker，因此不能把 LIFF 內的 Web Push 當成唯一背景通知方案。
- Web Push 的 VAPID 私鑰與推播訂閱端點視為秘密資料，存放於安全的 Worker secret／受限資料表，不提交 Git，也不回傳給無權限前端。
- 推播失敗、訂閱失效或使用者關閉權限時，系統內通知仍保留；後台可看到通道狀態，但不把通道失敗誤認成保姆已讀。
- 背景通知只用於即時、重要或需要採取動作的事件，不把所有資料異動都推播到手機。
- 背景通知的主要事件包括：
  - 客戶送出新預約／新訂單時通知經營者。
  - 經營者向保姆發出新工作邀請或完成新訂單指派時通知該保姆。
  - 已指派訂單發生改期、取消、服務地址變更或其他重大內容調整時通知該保姆。
  - 即將到來的家訪／服務提醒，以及經營者明確發出的重要訊息。
  - 保姆結算完成等個人帳務通知可由保姆選擇是否接收背景通知。
- 一般客戶資料異動、已處理紀錄、普通評價或低優先系統資訊只進通知中心，不發背景推播。
- 保姆尚未接受工作邀請前，背景通知與邀請摘要只顯示接案判斷所需資訊，例如日期、時段、服務類型與大致地區，不顯示客戶完整地址與敏感資料；正式指派後才依權限提供服務地址。
- 每筆背景通知都對應一筆系統內通知；點擊後開啟相關訂單或工作邀請，並分開記錄送達、打開、接受／拒絕與已知悉狀態。

### 後台角色與權限

| 功能／資料 | 經營者／最高管理員 | 保姆 | 客戶 |
|---|---|---|---|
| 客戶、毛孩、訂單總覽 | 可完整管理 | 僅限自己被指派的服務所需資料 | 僅限本人與自己的毛孩／訂單 |
| 服務地址 | 可查看目前地址、歷史與訂單快照 | 僅限被指派訂單的服務地址 | 僅限自己的地址與訂單地址 |
| 訂單金額與價格 | 可新增、修改、確認與補正 | 可看執行服務所需金額範圍；不得任意改客戶總額 | 可看自己的訂單金額 |
| 抽成與收益 | 可看全部保姆、Pinyu 抽成及總收益 | 只看自己的比例、應得與結算 | 不可查看內部分潤 |
| 保姆指派 | 可指派、改派與確認 | 可查看／回應自己的指派 | 可查看該單服務保姆的適當公開資訊 |
| 家訪費 | 可與保姆討論並確認列入訂單 | 可提出原因與建議金額 | 可查看自己訂單中已確認的費用 |
| 合約與敏感文件 | 依工作需要完整管理並留下稽核 | 只看自己簽署或被指派案件必要內容 | 只看自己的合約與副本 |
| 通知中心 | 可看全部管理通知 | 只看自己的指派、行程、客戶異動與結算相關通知 | 只看自己的操作結果與必要提醒 |
| 系統設定與錯誤 | 可管理 | 不可管理 | 不可管理 |

- 權限不能只靠前端隱藏選單，伺服器 API 與資料庫也必須驗證角色、資料所有權及訂單指派關係。
- 角色與授權資料不得使用客戶可自行修改的 user metadata；需使用受控的角色／成員資料或 app metadata，並在權限變更後處理登入狀態更新。
- 所有涉及地址、合約、收益與敏感資料的查詢欄位需有相應索引與資料列權限，避免資料量增加後權限檢查拖慢後台。

### 客戶會員端（第二階段）

- 客戶可建立、查看與修改自己的基本資料。
- 客戶可建立、查看與修改自己的毛孩資料，並支援一位客戶有多隻毛孩。
- 建立合約草稿時，自動帶入客戶及相關毛孩的既有資料，減少重複輸入。
- 客戶可在簽署前修改或補正合約草稿中的帶入資料；已簽署完成的合約版本不得因會員資料日後變更而被改寫。
- 客戶自行建立新訂單／送出預約不是近期第一優先，待管理後台訂單流程穩定後再優化。
- 目前客群以舊客戶為主，舊客與新客比例約為 `8:2`。

### 客戶地址與地址歷史

- 現行 Google Sheets 因個資與治安疑慮未保存完整地址；新系統可在完成權限保護後，將地址納入客戶會員資料。
- 客戶可有一個目前主要地址，也可保留舊地址的生效與停用時間；搬家時新增地址版本，不直接覆蓋到無法追溯。
- 新訂單預設帶入目前有效地址與對應車馬費，平常不要求每張訂單重複確認；客戶搬家或本次服務地點例外時再修改。
- 客戶自行修改地址後，新的會員地址立即生效並成為後續新訂單預設值，同時保留前一地址歷史並建立後台通知。
- 地址自動生效不得自動改寫已成立訂單；若已有未來服務訂單，後台通知列出相關訂單，由經營者決定是否逐單修改與重新計算車馬費。
- 每張正式訂單保存當時實際服務地址與車馬費快照，因此搬家前後訂單會各自顯示正確資料。
- 地址變更保留修改時間、修改者及必要原因；後台可查看客戶地址歷史與相關歷史訂單。
- 客戶只能查看與修改自己的地址；經營者可依工作需要管理完整地址歷史；保姆只能查看自己被指派訂單執行服務所需的地址，不得瀏覽客戶全部地址歷史。
- 地址資料不得透過公開頁面、永久公開網址或未經驗證的 API 取得；前端不得包含 Supabase secret／service-role 金鑰。

### 毛孩資料與多選標籤

- 毛孩的固定單一資料使用一般欄位，例如姓名、物種、品種、性別、生日、體重及是否結紮。
- 個性、喜好、行為與照護特徵使用可多選標籤，例如「愛吃」、「好動」、「活潑」，不為每一個新標籤建立一個資料表欄位。
- 資料庫分開保存「可選標籤清單」與「毛孩選了哪些標籤」；毛孩選三個標籤時只建立三筆關聯，不產生大量空白欄位。
- 標籤可依類別整理，例如個性、飲食偏好、社交反應、活動程度、醫療／照護提醒，方便客戶選擇及後台搜尋。
- 同一隻毛孩不得重複套用相同標籤；刪除或停用標籤時不得破壞既有毛孩歷史資料。
- 預設標籤由後台維護，客戶端以標籤按鈕多選；另提供補充說明欄，記錄標籤無法完整表達的細節。
- 標籤可附加必要補充，例如選擇「怕生」後補充觸發情境；重要健康與用藥資訊不得只靠模糊標籤，需使用明確欄位或照護說明。
- 後台可依標籤搜尋毛孩，例如找出所有「怕生」或「需餵藥」的毛孩；資料關聯欄位需建立適當索引。
- 客戶只能管理自己的毛孩資料；保姆只能查看被指派訂單中執行服務所需的毛孩資訊，經營者可依工作需要完整管理。

### 待確認規則

- 客戶在合約草稿補正資料時，是只修改該份合約，還是經客戶確認後同步更新會員主資料。
- 後台評價是否需要回覆、標記已處理、內部備註、隱藏或申訴等管理功能。
- 客戶是否只能選擇後台提供的標籤，或可以自行新增新標籤；若可新增，是否需由後台審核後才進入共用清單。
- 客戶修改地址後，是否也要透過 LINE 傳送一則變更確認給客戶，避免帳號誤操作或地址打錯未被發現。

### 正式切換最低條件

- 逐項盤點目前 Google Sheets 與 Apps Script 中實際會查看、輸入、修改、計算、搜尋及匯出的工作，建立功能對照表。
- 所有仍在使用的日常操作都已在新後台完成，或有經營者確認可接受的新流程；不得因資料已搬入 Supabase 就提前停用 Google Sheets。
- 經營者能在新後台獨立完成至少一輪真實情境：建立／修改客戶與毛孩、建立／修改／確認訂單、登記付款、查看尾款、指派保姆、核對抽成、查看評價及處理行事曆同步。
- 重要資料與計算結果完成新舊系統核對，並在平行測試期間確認沒有漏單、重複訂單或金額不一致。
- 完成切換前最後一次 Google Sheets 差異匯入、備份與回復舊系統方案後，才可把正式 LINE／網域導向新系統。

### 儲值功能範圍

- 現行「儲值扣款」功能目前沒有實際使用，不列入第一階段新後台的新增訂單與付款流程。
- 已匯入的歷史儲值與扣款資料先保留作為歷史紀錄，不因停用功能而刪除。
- 未來若確定重新啟用儲值，再另行確認餘額、退款、到期、撤銷與對帳規則後實作，不直接沿用現有試算表扣款程式。

## 1. 保姆團隊、轉介抽成與收益統計

### 合作模式定位

- Pinyu 不是讓不特定保姆自由上架接案的媒合平台。
- 合作保姆皆由經營者親自培訓、帶領、實際合作並確認服務品質後，才納入 Pinyu 團隊。
- 合作保姆仍可自行對外接案；保姆自己取得的客戶與訂單不向 Pinyu 支付抽成。
- 只有由 Pinyu／經營者轉介或分派給合作保姆的訂單，才依該張訂單約定的比例計算 Pinyu 轉介／管理抽成。
- 系統需記錄訂單來源，至少區分「Pinyu 轉介」、「保姆自行接案」與「經營者本人服務」，避免不該抽成的訂單被計入。

### 服務地區、可預約時間與保姆選擇

- 每位保姆可設定自己願意服務的地區，不公開精確住址；可依行政區／郵遞區號等穩定方式管理主要服務區與例外區域。
- 每位保姆可設定可提供的服務類型、毛孩類型／限制、專長與適合情境，作為客戶判斷是否符合需求的資料。
- 客戶自行預約時先輸入服務地區、日期／時段、服務類型與毛孩需求，再顯示符合基本條件的保姆。
- 客戶可選擇偏好的保姆，也可選擇「不指定／由 Pinyu 安排」；是否最終指派仍需依保姆可接單狀態與業務流程確認。
- 客戶看到的是保姆公開簡介、服務區域、可提供服務、適合條件、可選時段與適當價格資訊，不公開保姆詳細住址或完整私人行程。
- 保姆可設定固定每週可預約時段、臨時不可接案日期、暫停接新單，以及接單容量限制。
- 第一階段接單容量以「每月最多幾張已確認需求單」計算，同一需求單的多個服務項目不重複計數；未來仍預留改用服務次數或服務時數的可能。
- 品伃的既有固定忙碌規則為週一至週五 09:00–18:00；容容採不固定班別，可用早班、午班、晚班快捷鍵設定單日可接時間。
- 已成立訂單與服務時段會占用可預約容量；改期、取消與完成需正確釋放或結算容量，避免重複預約。
- 顯示給客戶的價格需區分預估與正式報價；因服務價格可能依客戶、保姆與個案客製，未確認前不得把預估價誤當成保證成交價。

### 分階段派單方向

1. 第一階段：經營者在管理後台建立訂單、查看保姆服務區與可用時間，再由後台指派或發出工作邀請。
2. 第二階段：客戶自行填寫需求、選擇偏好保姆或不指定，系統先產生預約申請／待確認訂單。
3. 最終階段：依實際營運決定由經營者確認、保姆接受，或在符合限制時自動指派；目前不採用未規劃好的多人搶單規則。
4. 客戶選擇保姆是否代表保證指派、僅是偏好，及保姆／經營者的確認順序，留待客戶預約流程設計時決定。

### 目前問題

- 舊試算表主要以經營者本人執行服務為前提，沒有完整容納其他保姆與分潤的結構。
- 保姆抽成比例不是永久固定，可能依熟練度、時間或個別訂單調整。
- 需要同時看見客戶訂單金額、保姆實得、經營者本人服務收入、Pinyu 轉介／管理抽成收入與合計收入。

### 必要功能

- 建立保姆資料與啟用狀態。
- 每張訂單或服務項目可以指定實際執行的保姆。
- 保姆可以有「目前預設抽成比例」以及有生效日期的歷史調整紀錄。
- 個別訂單可覆寫預設抽成比例。
- 訂單成立時保存該單實際採用的抽成比例快照；日後調整預設比例時，歷史訂單不得跟著改變。
- 保留並計算下列金額：
  - 折扣前總價
  - 折扣金額
  - 客戶折扣後應付總額
  - 抽成計算基礎金額
  - Pinyu 轉介／管理抽成比例
  - Pinyu 轉介／管理抽成金額
  - 保姆實得金額
  - 經營者本人親自服務的收入
  - 經營者由其他保姆訂單取得的抽成收入
  - 經營者服務收入加 Pinyu 轉介／管理抽成收入的合計
- 後台可依保姆與日期範圍查看：訂單、折扣前金額、折扣後金額、抽成比例、抽成金額、保姆實得與是否已結算。
- 預留一張訂單由多位保姆或不同服務項目分別執行的能力，避免未來再次重做資料結構。

### 已確認規則

- 客戶折扣由經營者／Pinyu 端吸收，不扣減保姆原本應得的服務報酬。
- 系統仍須同時保存折扣前金額、折扣後實收與 Pinyu 實際收入，讓折扣成本可被清楚追蹤。
- 保姆報酬以「折扣前、可參與分潤的服務金額」及該張訂單保存的抽成比例快照計算；客戶折扣不得進入保姆報酬公式。
- 保姆報酬唯一會因業務設定而改變的因素是該單採用的抽成比例；同一張訂單的比例一旦確認，日後修改保姆預設比例不得回頭改動歷史金額。
- 計算示例：折扣前 4,000 元、客戶折扣後支付 3,600 元、Pinyu 轉介／管理抽成 20% 時，保姆仍取得 3,200 元；400 元折扣由 Pinyu 收入吸收，Pinyu 該單實得 400 元。
- 客戶指定給保姆的小費 100% 歸實際服務的保姆，Pinyu 不抽成。
- 車馬費屬於實際服務保姆的交通補貼，100% 歸保姆，Pinyu 不抽成。
- 成熟派單流程會優先詢問並分派所在地區合適的保姆，因此多數訂單車馬費可為 0；確有跨區或額外交通成本時再個別收取。
- 第一次到府家訪／評估原則免費，但若有車馬費仍可另外收取；第二次或後續家訪若考慮收費，由實際服務保姆依個案提出，並與經營者討論確認，不由任何一方單方面固定決定。
- 後台需讓保姆提出後續家訪費用與原因，經營者確認後才列入客戶訂單；金額可依個案調整，不設定成無法覆寫的固定價格。
- 車馬費會依保姆所在地與事主服務地點而變化；系統建立共用計算原則，同時允許依個案填寫或調整。

### 待確認規則

- 雙方確認收取後續到府評估費時，該費用是否納入 Pinyu 轉介／管理抽成。
- 加購項目是否納入 Pinyu 轉介／管理抽成。
- 一張訂單由多位保姆執行時，金額如何分配。
- 已取消、退款、補款或超收時如何回沖保姆收入與 Pinyu 收入。
- 客戶選擇特定保姆是保證指派，還是偏好申請後仍需保姆／經營者確認。
- 保姆容量以每月訂單數、服務次數、服務時數或混合方式限制。
- 多位保姆同時符合「不指定」需求時的排序、詢問與最終指派規則。
- 客戶端顯示保姆價格的範圍、預估方式與正式報價時點。

## 2. 訂單卡片與金額對帳

### 目前問題

- 訂單在確定、已付訂金或已完成等狀態下，卡片沒有清楚顯示該次尚未支付的尾款。
- 服務項目右側目前可能只顯示單價，例如顯示 900；另一處又顯示該項合計 3,600，導致右側數字相加不等於訂單總額。

### 必要顯示方式

- 每一個服務項目都顯示完整算式：`單價 × 次數（或時數）＝項目小計`。
- 右側主要金額顯示「項目小計」，不是只顯示單價。
- 所有項目小計加上額外費用、扣除折扣後，必須可以逐項對回最後總金額。
- 折扣、車馬費、到府評估費、加購、小費等不能藏在總額裡，應以獨立加減項目呈現。
- 訂單摘要與明細至少顯示：
  - 折扣前總價
  - 折扣金額
  - 訂單總金額
  - 已收訂金或累計已付款
  - 未付尾款
- 訂單狀態不得取代付款狀態；即使訂單為「已確認」或「已完成」，仍要顯示未付尾款。
- 尾款已結清時明確顯示 `未付尾款 0 元／已結清`。
- 未付尾款應由訂單應付金額與有效付款紀錄計算，不能只靠人工文字欄位。
- 每筆加減項目需保存「類型、金額、最終歸屬、是否參與抽成」；例如車馬費與小費的歸屬皆為保姆且不參與抽成，避免後台用人工另算。

## 3. 電子合約與敏感資料權限

### 目標

- 合約可在後台建立、簽署、保存與查閱，減少紙本並方便需要權限的保姆查看必要資訊。
- 基本資料以打字輸入，避免全部手寫造成辨識困難。
- 簽名保留手寫簽署，可在手機或平板簽名區完成。

### 必要功能

- 合約範本具版本號；已簽署合約保留當時版本，不因日後修改範本而改變。
- 基本資料欄位可輸入並在簽署前預覽。
- 手寫簽名、簽署時間與簽署事件紀錄需和合約綁定。
- 簽署完成後產生不可任意覆寫的合約版本，雙方可取得自己的副本。
- 記錄建立、查看、簽署、下載與作廢等稽核事件。

### 權限初稿

- 經營者／授權管理員：依工作需要查看完整合約與敏感資料。
- 保姆：只能查看分派給自己且工作所需的合約內容，不得查看其他保姆或無關客戶資料。
- 客戶：只能查看自己的合約與簽署副本。
- 身分證號在一般畫面遮罩，只在確有需要且有權限的流程中顯示完整內容。
- 身分證圖片與其他敏感文件存放在 Supabase 私有 Storage，不使用永久公開網址。
- 文件下載需經身分與權限檢查，使用短效存取連結，並留下查看／下載紀錄。
- 採最少蒐集原則；實際需要保存哪些身分資料、保存多久與如何刪除，需在正式上線前確認。

### 待確認規則

- 第一階段要製作的是客戶服務合約、保姆合作合約，或兩者都要。
- 哪些欄位屬於所有保姆工作必要資訊，哪些只能由經營者／管理員查看。
- 身分證是否需要上傳正反面影像，或只需驗證／保存部分欄位。
- 合約修改、補簽、撤銷與重新簽署的流程。
- 電子簽署文字、個資告知與保存期限在正式使用前需另行確認。

## 4. Google 行事曆自動建立行程

### 目標

- 訂單確認成立後，自動把服務行程建立到經營者的 Google 行事曆，不必再手動建立一次。
- 行程需帶入執行服務時會用到的客戶與訂單資訊，例如服務日期、時間、地址與訂單識別資訊。

### 必要功能

- 只有達到指定的「訂單已確認」條件時才建立行事曆事件，避免尚未成立的預約先佔用正式行程。
- 一張訂單若包含多個服務日期或時段，系統可分別建立對應的行事曆事件。
- 保存 Google Calendar event ID，後續訂單改期、改地址、取消或更換保姆時，可以更新或取消原事件，而不是重複新增。
- 管理員把訂單確認為「待執行」時，必須同時占用保姆排班並建立 Google Calendar 同步工作；Google 暫時失敗不能使訂單建立失敗，需保留待同步／失敗狀態與重試紀錄。
- 建立、更新與取消需有狀態、錯誤訊息與重試機制，避免系統顯示成功但行事曆實際沒有建立。
- 行事曆內容只放執行服務必要資訊；敏感個資不得無限制寫入共用行事曆。
- 未來若有多位保姆，可依實際指派同步到指定保姆有權查看的行事曆。

### 待確認規則

- 每個服務時段各建立一筆事件，或整張訂單只建立一筆事件。
- 第一階段只同步經營者本人的行事曆，或同時支援其他保姆的行事曆。
- 事件標題、說明欄與地址欄各自要顯示哪些客戶、寵物與服務資料。
- 訂單取消時刪除事件，還是保留並標記為取消。

## 建議實作順序

1. 盤點現有訂單、價格、付款與狀態規則。
2. 確认抽成基礎、折扣分攤及額外費用是否抽成。
3. 完成訂單、服務項目、付款、保姆指派、抽成快照與結算的資料模型。
4. 先完成經營者登入、後台總覽、客戶／毛孩查找，以及訂單列表、詳情、新增／修改與金額對帳。
5. 完成後台評價、保姆收益、經營者收入報表與 Google 行事曆同步。
6. 建立客戶會員資料與毛孩資料的建立／修改功能。
7. 規劃並實作可帶入會員資料的電子合約、私有文件與角色權限。
8. 最後再優化客戶自行送出預約流程，並共用同一套已驗證的計價與訂單 API。
9. 串接 LINE 通知與排程後進行平行測試。
