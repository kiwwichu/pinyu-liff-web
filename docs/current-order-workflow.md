# 現行訂單與試算表自動化流程

盤點日期：2026-08-19
來源：2026-08-19 正式 Apps Script 匯出版本

## 核心結論

- 現行 Apps Script 沒有完整的「新增訂單」API 或表單處理函式。
- 一張邏輯訂單在「需求單」分頁以多列服務項目保存，訂單共同欄位會在相同需求單編號的多列之間同步。
- 經營者目前主要仍在 Google Sheets 直接新增／複製／修改需求單列，再由 `onEdit` 與時間觸發器執行後續自動化。
- `doPost` 雖檢查 `handleAdminPortalRequest_` 是否存在，但本次正式匯出的 19 個檔案中沒有該處理函式；現有管理後台不是一條可直接搬用的完整新增訂單後端。
- 新管理後台的新增訂單必須重新建立一個完整、可驗證且以整張訂單為單位的流程，不能只模仿新增試算表列。
- 經營者目前會依個案選擇直接新增列或複製舊訂單再修改；新後台需保留兩種操作彈性。
- 現行儲值扣款沒有實際使用，第一階段不搬成可操作的新功能；歷史資料仍保留。

## 主檔與訂單快照

- 客戶會員主檔保存「目前」的聯絡資料與預設地址，毛孩主檔保存目前照護資料。
- 訂單仍關聯到客戶與毛孩，但同時保存成立當下實際使用的服務地址、聯絡資訊、服務內容、單價、車馬費、折扣、分潤比例與其他必要快照。
- 客戶搬家後更新會員主檔，新訂單預設帶入新地址；搬家前訂單繼續顯示舊地址與舊車馬費。
- 價目表、車馬費規則或保姆預設抽成變更後，只影響新建立的訂單，不重新套用到已確認訂單。
- 複製舊訂單時，後台需提示「舊訂單地址」與「會員目前地址」是否不同，讓經營者選擇本次採用資料並重新確認金額。
- 歷史訂單不使用會隨主檔變更而自動重算的公式；必要補正需留下修改者、時間、原因與前後值。
- 客戶地址另外保留版本歷史；新訂單使用目前有效地址，保姆只取得被指派訂單的實際服務地址，不取得客戶全部地址紀錄。

## 服務價格的三層結構

1. 服務大分類與一般參考價格：提供一致分類與建立新訂單的基本選項。
2. 客戶約定價格：保存該客戶目前有效的客製單價與歷史生效時間。
3. 訂單項目快照：保存該次真正採用的名稱、單價、數量、小計與人工調整內容。

- 新增訂單時先帶入客戶約定價；沒有約定價時再使用一般參考價。
- 經營者可在單次訂單內修改價格或加入一次性自訂項目，不需要為每個特殊價格新增永久下拉選項。
- 後台顯示價格來源；訂單確認後不因分類參考價或客戶約定價更新而改變。

## 編輯試算表後會發生的事情

| 使用者修改的內容 | 舊系統自動動作 | 新後台對應方向 |
|---|---|---|
| 折扣或總價 | 重新計算該列折扣後總價 | 訂單計價引擎即時預覽並由後端再次驗證 |
| 建立時間 | 同步到相同需求單編號的所有列 | 訂單只保存一份建立時間，不需跨列同步 |
| 需求單狀態 | 同步同單所有列；依狀態新增／更新或刪除到府明細 | 單一訂單狀態事件，交易式更新服務時段 |
| 狀態改成完成 | 刪除該單未鎖定的到府明細，保留鎖定列 | 明確完成流程；保留服務歷史，不用物理刪除重要紀錄 |
| 到府明細指令 | 清除未鎖定舊資料並重建服務明細，回寫成功／失敗註記 | 後台「重新產生服務時段」工具，顯示預覽、結果與錯誤 |
| 通知指令設為發送 | 每分鐘佇列掃描後，依訂單狀態發送對應 LINE 通知 | 明確通知工作、狀態、防重、重試與最後錯誤 |
| 是否使用儲值金 | 建立扣款列；取消時嘗試刪除扣款紀錄，但目前未實際使用 | 第一階段不提供新扣款操作；保留歷史資料，未來啟用時重新設計 |
| 到府明細時段代碼 | 回填時段文字並自動鎖定該列 | 服務時段有明確的人工調整／鎖定狀態與修改紀錄 |

## 訂單狀態與通知

| 訂單狀態 | 待發通知 |
|---|---|
| 常客／未付訂金 | 訂單確認通知 |
| 待執行 | 訂單成立通知 |
| 待付尾款／未付尾款／常客－待付尾款 | 尾款通知 |
| 完成 | 完成通知與評價入口 |

- 通知成功後會清空「通知指令」，避免同一指令重複發送。
- 通知失敗時目前也會清空「通知指令」，因此不會自動重試；修正資料後需要人工再次選擇發送。

## 搬遷時必須修正的舊問題

1. 折扣輸入說明聲稱支援「9折、95折、9、95」，實際解析程式只接受 `0.9`、`0.95` 這類 0 到 1 的數字。
2. 同一訂單有多列服務時，從某一列勾選儲值扣款會讀取該列金額，可能不是整張訂單的折扣後應付總額；此功能目前未使用，第一階段不沿用。
3. 建立儲值扣款寫入「儲值流水」，取消時卻呼叫刪除「扣款自動表」紀錄，存在帳務未正確回沖的風險；歷史資料保留，但不把舊邏輯搬入新操作流程。
4. 通知失敗後清空發送指令，沒有自動重試、重試次數或下次重試時間。
5. 訂單成立通知會檢查 LINE 發送結果；尾款與完成通知的佇列流程沒有同等完整的成功判定，可能錯把失敗標成已通知。
6. 兩套通知處理函式對狀態採用「完全相等」與「文字包含」兩種不同判斷方式，可能產生同一狀態在不同入口結果不一致。
7. 完成訂單時會刪除未鎖定到府明細；新系統應以保留服務歷史與取消／完成狀態為原則，避免為了畫面整理而刪除可稽核資料。
8. 正式程式引用 `handleAdminPortalRequest_`，但匯出專案中沒有實作；管理後台 API 需重新建立並加上正式身分驗證與權限。

## 新後台新增訂單的最低完整流程

1. 選擇或新增客戶與毛孩。
2. 新增一或多個服務項目、日期／時段、單價、次數與執行保姆。
   - 可從服務大分類選擇，優先帶入客戶約定價格，也允許本單人工調整或一次性自訂項目。
3. 加入車馬費、小費、家訪費、加購與折扣等獨立項目，並標記歸屬與是否抽成。
4. 顯示折扣前總價、折扣、應付總額、訂金、已付款與未付尾款；第一階段不提供新的儲值抵扣操作。
5. 驗證每個項目小計與最終總額完全對得上。
6. 先保存草稿；確認後才建立正式訂單與服務時段。
7. 保存該單保姆分潤比例快照與金額歸屬。
8. 訂單確認後建立 Google 行事曆事件，並產生可追蹤的 LINE 通知工作。
9. 所有重要修改保留操作者、時間與前後內容，取消或修正使用反向紀錄，不直接刪除帳務與服務歷史。
